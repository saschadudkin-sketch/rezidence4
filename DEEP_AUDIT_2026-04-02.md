# Единый deep audit веб-приложения (UI/UX + Frontend Architecture)

**Дата аудита:** 2026-04-02  
**Роль:** Senior UI/UX Designer + Senior Frontend Architect  
**Метод:** код-аудит + запуск тестов + частичная проверка сборки.

---

## 0) Executive summary

Приложение уже не выглядит «сырой демкой» по объёму функционала и количеству тестов, но системно остаётся **операционно-ориентированным интерфейсом с высокой когнитивной нагрузкой** и **монолитным UI-слоем**, где один большой CSS-файл и крупные компоненты усложняют масштабирование.

Ключевая связка проблем:

- **UX/UI:** в навигации и CTA много role-based вариативности, но нет явных «guiding patterns» для пользователя; пользователю приходится помнить контекст.  
- **Frontend:** логика управления ролями, табами, бейджами и живой синхронизацией распределена по нескольким хукам/вьюхам, но визуальный слой централизован в одном `theme.css`, что повышает риск регрессий.  
- **Performance/Responsive:** есть зачатки оптимизации (lazy, memo), но остались признаки «ручной оптимизации точечно» вместо системного подхода (дизайн-система, токены, композиция компонентов, бюджет bundle).

---

## 1) Объём проверки

Проверены ключевые области:

- UX-флоу логина и дашборда (role-based navigation, статусы, CTA).
- Визуальная система и responsive-слой.
- Архитектура фронтенда (store, hooks, services, API clients).
- Перформанс-паттерны на уровне React + CSS.
- Надёжность по тестам и сборке.

Команды проверки:
- `npm --prefix frontend test` — **успешно** (83 файла тестов, 827 passed).  
- `npm --prefix frontend run build` — **ошибка окружения**: отсутствует `VITE_API_URL` для production build.  
- `npm --prefix backend test` — **массовые падения** (13 suite failed, 75 tests failed), включая auth/csrf/permissions/chat/visitLogs.

## 2) Каталог проблем (связанный UX + UI + Tech)

> Формат: **ID / Приоритет / Категория / Где / Проблема / Почему плохо / Причина / Как исправить**

### A-01
- **Приоритет:** критично  
- **Категория:** Architecture / Frontend / UX  
- **Где:** `frontend/src/views/Dashboard.jsx`
- **Проблема:** Дашборд остаётся «оркестратором всего» (навигация, хедер, профиль-меню, загрузка, lazy-view switch, mobile nav).  
- **Почему плохо:** сложно эволюционировать UX-паттерны (например, wizard/onboarding, role-specific IA) без риска ломать другие зоны.  
- **Причина:** исторически фича-рост вокруг единого контейнера.  
- **Как исправить:** выделить layout shell + navigation shell + role router как независимые композиционные компоненты; оставить Dashboard только как coordinator сценария.

### A-02
- **Приоритет:** важно  
- **Категория:** UI / Architecture  
- **Где:** `frontend/src/styles/theme.css` (единый файл ~2000+ строк)
- **Проблема:** глобальный CSS-файл содержит почти всю систему визуала, responsive, states, утилиты.  
- **Почему плохо:** высокий coupling между фичами, трудная дифф-ревизия, риск side effects при любом визуальном изменении.  
- **Причина:** отсутствие модульной дизайн-системы (tokens + component styles + layout primitives).  
- **Как исправить:** перейти к layered styling: `tokens.css` → `foundations.css` → `components/*` → `features/*`; плюс визуальные regression tests.

### A-03
- **Приоритет:** важно  
- **Категория:** UX / UI / Responsive  
- **Где:** `Dashboard` top nav + mobile nav
- **Проблема:** две разные навигационные модели (desktop top-nav с текстом и бейджами, mobile bottom-nav с dot-индикаторами) несут разную информативность.  
- **Почему плохо:** пользователь на мобильном теряет контекст количества и типа новых событий (dot без числового значения).  
- **Причина:** разные визуальные компромиссы без единой информационной иерархии.  
- **Как исправить:** унифицировать семантику сигналов: на mobile показывать count caps (1–9+) и приоритетные типы уведомлений; добавить legend/pattern consistency.

### A-04
- **Приоритет:** критично  
- **Категория:** Frontend / Security / Reliability  
- **Где:** backend test baseline
- **Проблема:** backend regression footprint высокий (auth/csrf/perms/chat/visit logs тесты массово падают).  
- **Почему плохо:** UX-качество интерфейса не имеет значения, если базовые сценарии авторизации и API нестабильны.  
- **Причина:** рассинхрон изменений API/мидлваров и тестовых контрактов.  
- **Как исправить:** стабилизировать контрактный слой (OpenAPI + contract tests в CI gate), затем фиксить auth/csrf пути как блокер релиза.

### A-05
- **Приоритет:** важно  
- **Категория:** UX / Product  
- **Где:** Login flow (`frontend/src/views/Login.jsx`)
- **Проблема:** двухшаговый вход «телефон → OTP» без прогресс-индикатора этапов и без явной причины ошибок (кроме toast).  
- **Почему плохо:** при ошибках пользователь может повторять действие, не понимая текущее состояние и что делать дальше.  
- **Причина:** toast-first feedback вместо form-bound feedback.  
- **Как исправить:** добавить stepper (1/2), inline-error у поля, disable policy с явной причиной, resend countdown.

### A-06
- **Приоритет:** желательно  
- **Категория:** UI / SaaS maturity  
- **Где:** визуальный язык (theme variables + mixed component patterns)
- **Проблема:** хороший токен-базис есть, но разные зоны используют разные паттерны плотности, заголовков, карточек и статусов.  
- **Почему плохо:** интерфейс ощущается как «набор экранов», а не единая SaaS-платформа.  
- **Причина:** постепенное развитие фич без формальной design system governance.  
- **Как исправить:** ввести UI kit уровня продукта (card, form row, section header, badge semantics, state placeholders) и запрет новых ad-hoc вариантов.

### A-07
- **Приоритет:** важно  
- **Категория:** Performance / Frontend  
- **Где:** `Dashboard.jsx`, `theme.css`, role views
- **Проблема:** оптимизации есть (memo/lazy), но скорее реактивные; нет измеримого perf budget и профилирования как процесса.  
- **Почему плохо:** деградации будут накапливаться незаметно (особенно в role-specific экранах и чате).  
- **Причина:** отсутствие performance governance (bundle budget, React profiler CI checks).  
- **Как исправить:** добавить bundle analyzer в CI, лимиты на chunk size, профили hot-path (chat/list/filters), telemetry по TTI/INP.

### A-08
- **Приоритет:** важно  
- **Категория:** UX / Loading/Error states  
- **Где:** dashboard sync flow + API error surfaces
- **Проблема:** есть глобальный loading-state и toasts, но не везде системно показаны retry-able ошибки на уровне конкретного блока/виджета.  
- **Почему плохо:** пользователь не понимает, упала ли конкретная часть данных или всё приложение.  
- **Причина:** централизованный sync и фрагментарные error-boundary подходы.  
- **Как исправить:** ввести state model per widget: `idle/loading/success/error/empty` + локальный retry.

### A-09
- **Приоритет:** желательно  
- **Категория:** Responsive / Usability  
- **Где:** плотные таблицы/grid блоки и скрытие колонок на узких экранах
- **Проблема:** в мобильных брейкпоинтах часть данных просто скрывается, вместо альтернативного представления.  
- **Почему плохо:** теряется объяснимость интерфейса, пользователь может не видеть критичную информацию.  
- **Причина:** CSS-driven hide strategy вместо adaptive content strategy.  
- **Как исправить:** для мобильного использовать stacked-card rows или disclosure-паттерн «основное + раскрытие деталей».

### A-10
- **Приоритет:** важно  
- **Категория:** Frontend / API / State management  
- **Где:** AppStore + provider layer
- **Проблема:** store разбит по доменам (это плюс), но сервисный слой всё ещё требует дисциплины ручной синхронизации между live/demo режимами и множеством setAll* экшенов.  
- **Почему плохо:** риск рассинхрона данных и непредсказуемых UX-эффектов при частичных обновлениях.  
- **Причина:** кастомный state+service orchestration без стандартизированного data fetching framework.  
- **Как исправить:** рассмотреть migration path на React Query/TanStack Query (или аналог) для кеша, retry, stale policies, error boundaries.

### A-11
- **Приоритет:** желательно  
- **Категория:** UX / Cognitive load  
- **Где:** role-based tabs + badges
- **Проблема:** разные роли видят разные структуры и labels; ментальная модель «куда нажать для X» плохо переносится между ролями.  
- **Почему плохо:** обучение персонала и кросс-рольная поддержка сложнее.  
- **Причина:** роль диктует интерфейс полностью, без shared skeleton.  
- **Как исправить:** сохранить role filtering, но ввести общее «каркасное» расположение и единые названия базовых разделов.

### A-12
- **Приоритет:** важно  
- **Категория:** Security / Frontend  
- **Где:** production build dependency on env + runtime config
- **Проблема:** сборка жёстко падает при отсутствии `VITE_API_URL`; это хорошо как guardrail, но нет documented fallback и preflight check script на CI.  
- **Почему плохо:** релизная pipeline может ломаться поздно, а не на ранней стадии.  
- **Причина:** недостаточно формализованный release contract.  
- **Как исправить:** добавить `npm run verify:env` и schema validation env на уровне CI до build/test.

### A-13
- **Приоритет:** желательно  
- **Категория:** UI / Accessibility  
- **Где:** глобальные focus/outline правила в CSS
- **Проблема:** `*:focus{outline:none}` + reliance on `:focus-visible` может дать edge-case недоступности в нестандартных браузерах/сценариях.  
- **Почему плохо:** keyboard accessibility может деградировать незаметно.  
- **Причина:** агрессивный global reset.  
- **Как исправить:** ограничить reset к конкретным контролам и ввести a11y regression checks (axe/playwright).

### A-14
- **Приоритет:** важно  
- **Категория:** Architecture / Maintainability  
- **Где:** frontend views/hooks/services
- **Проблема:** есть много «fix-комментариев» в коде как история инцидентов.  
- **Почему плохо:** код становится журналом патчей, а не декларативной архитектурой; onboarding дорожает.  
- **Причина:** процесс ориентирован на быстрые локальные правки.  
- **Как исправить:** перенести исторический контекст в ADR/CHANGELOG, а код очистить до intent-focused комментариев.

### A-15
- **Приоритет:** важно  
- **Категория:** Performance / Data / UX  
- **Где:** live sync + badges + chat
- **Проблема:** real-time логика распределена и может вызывать частые мелкие обновления интерфейса.  
- **Почему плохо:** на слабых устройствах это приводит к «дерганности», особенно при одновременных updates в чат+заявки.  
- **Причина:** множественные state updates без централизованного batching/selector memo strategy.  
- **Как исправить:** ввести селекторы с мемоизацией, пакетировать события sync, использовать transition/prioritized updates там, где допустимо.

## 3) Top-10 самых важных проблем

1. **Нестабильный backend-контракт (auth/csrf/perms/chat/visit logs) блокирует доверие к продукту.**  
2. **Монолитный Dashboard как точка высокой сложности и регрессионного риска.**  
3. **Единый огромный CSS-файл без модульной дизайн-системы.**  
4. **Непоследовательная информационная семантика desktop vs mobile nav.**  
5. **Слабая система локальных loading/error/retry состояний по виджетам.**  
6. **Высокая когнитивная нагрузка из-за role-variant IA и ярлыков.**  
7. **Точечная, а не системная performance-стратегия.**  
8. **Ручная оркестрация state/services повышает риск рассинхрона.**  
9. **Недостаточная формализация release/env контрактов.**  
10. **Неполная зрелость визуального языка как SaaS design system.**

## 5) Strategic improvements (системно)

1. **Frontend Platform Track (4–6 недель):**
   - модульная дизайн-система и UI kit,
   - архитектурный рефактор Dashboard в shell-композицию,
   - стандартизованный data fetching/caching слой.

2. **Product UX Track (3–4 недели):**
   - role-based IA harmonization,
   - критические user journeys с task success metric,
   - унификация CTA и пустых/ошибочных состояний.

3. **Reliability Track (2–4 недели):**
   - backend contract stabilization,
   - обязательные contract tests в CI,
   - release gating по auth/csrf/permission regression pack.

4. **Performance Track (2–3 недели):**
   - bundle budget + analyzer,
   - профилирование chat/list hot paths,
   - реал-тайм batching и memoized selectors.

## 6) Что мешает ощущаться как зрелый SaaS-продукт

1. **Непредсказуемость надёжности** (падающие backend-тесты в базовых сценариях).  
2. **UI-слой не оформлен как продуктовая система** (визуально «много хороших частей», но нет единого языка на уровне платформы).  
3. **UX-флоу больше про операционную функциональность, чем про guided experience.**  
4. **Архитектура всё ещё несёт следы «эволюции через патчи», а не через устойчивые контракты.**

Итог: чтобы перейти от «сильного MVP+/production prototype» к зрелому SaaS, нужно не столько добавлять фичи, сколько закрыть **три системных контура: contract reliability, design system governance, state/data platformization**.
