**Дата:** 28 октября 2026  
**Репозиторий:** `saschadudkin-sketch/rezidence4`  
**Проверенная основная ветка:** `main`, commit `487bfad6453d172e33624107623abf6497c7ffdc`  
**Мобильная ветка:** `codex/mobile-app-foundation`, PR [#154](https://github.com/saschadudkin-sketch/rezidence4/pull/154)

## 1. Краткий вывод

**Проект имеет серьёзную техническую основу и его рациональнее улучшать поэтапно, а не переписывать с нуля.** В нём уже есть многопользовательская архитектура, PostgreSQL/Redis, backend на Express, web-клиент на React/Vite, tenant resolver, OTP-сессии, журналирование, миграции, OpenAPI, тесты и release/readiness-скрипты.

Но наличие модулей, тестов и документов не доказывает, что вся система готова к производственной эксплуатации. По доступным данным готовность не подтверждена свежим зелёным CI, актуальной сборкой Android/iOS, испытаниями со СКУД и проверкой производственной конфигурации.

**Статус по этому аудиту:**
- Архитектура: есть база, но много контуров и compatibility-слоёв — нужна дисциплина границ.
- Web/backend: функционально развитый код; требуется свежая полная верификация.
- Мобильный клиент: только начальная оболочка, не готов к пилоту.
- Безопасность: реализованы полезные контроли; полноценный независимый аудит и runtime-проверки не проводились.
- Эксплуатация: deployment, резервное восстановление, уведомления и production evidence нужно подтвердить практическими проверками.

## 2. Объём и ограничения проверки

Проверены GitHub-дерево и ключевые файлы архитектуры, package manifests, README, CI, Docker Compose, auth, tenant middleware, CSRF/rate limiting, OpenAPI и readiness/security-документация.

В основной ветке найдено около 2 244 записей дерева, 461 путь в `backend/`, 666 в `frontend/`, 219 в `docs/`, 448 путей, соответствующих широкому шаблону тестов, и 67 путей с упоминанием миграций. Эти цифры — ориентиры размера репозитория, а не доказательство количества успешных тестов или качества покрытия.

Это **статический аудит исходников и конфигурации**, не полноценный penetration test. В этой проверке не выполнялись локальная установка зависимостей, полный test suite, миграции на чистой БД, нагрузочный прогон, проверка production-секретов, восстановление backup, физические Android/iOS сборки или тестирование реального оборудования. Выводы о непроверенных функциях отмечены как риски/неподтверждённые состояния, а не как доказанные уязвимости.

## 3. Что уже сделано хорошо

1. **Версионированный API.** В документации `/api/v1/*` определён как основной контракт, а старые `/api/*` оставлены для совместимости.
2. **Многоплощадочная модель.** Есть центральный реестр объектов и отдельный DB pool для объекта; resolver учитывает hostname, tenant header и claim токена и содержит защиту от несоответствия tenant.
3. **Сессии.** Access token короткоживущий; refresh token имеет ротацию и хранится в базе в хэшированном виде. Предусмотрены отзыв и проверки активности пользователя.
4. **Web-защита.** Есть Helmet, CORS allowlist, CSRF double-submit, запрет state-changing API-запросов без Origin и rate limiting.
5. **Ограничение OTP.** Код генерируется через CSPRNG, хэшируется, имеет срок действия и ограничение попыток; неизвестный номер не должен раскрывать наличие аккаунта.
6. **Операционная зрелость как цель.** Есть проверки OpenAPI drift, tenant scope, release gates, readiness для РФ, backup/restore tooling и threat model.
7. **Контейнеризация.** Backend запускается от непривилегированного пользователя; PostgreSQL и Redis в Compose описаны как внутренние сервисы; Redis защищён паролем.
8. **Продуктовый ориентир.** `PRODUCT.md` правильно разделяет спокойный mobile-first опыт жильца и более плотные интерфейсы сотрудников.

Эти элементы стоит сохранить и укрепить, а не выбрасывать при переписывании.

## 4. Приоритетные находки

### P0 — блокирует выпуск мобильного клиента в пилот

**MOB-01. Мобильные сценарии пока не подключены.**  
В `apps/mobile/` есть Expo/React Native shell, но ключевые кнопки на главном экране — заглушки. Нет полного native OTP/session lifecycle, живого списка/создания пропусков, push, интерфейса охраны и server-authoritative QR verification. Нет подтверждённых сборок и тестирования на устройствах.

**Рекомендация:** считать приложение prototype/internal preview. Не выдавать его охране как инструмент принятия решения о допуске.

### P1 — необходимо закрыть до производственного пилота

**SEC-01. Мобильный контракт авторизации не определён.**  
Существующий auth flow использует HTTP-only cookies и CSRF-механизм для браузера. Мобильный API helper намеренно не добавляет ни cookie, ни bearer-токен. Это не баг само по себе, но означает, что защищённые сценарии мобильного приложения не подключены.

**Рекомендация:** определить отдельный контракт нативной сессии (короткий access token, ротация/отзыв refresh token либо обоснованная альтернатива), хранить секреты только в secure storage ОС, сохранить существующий web flow и покрыть контракт интеграционными тестами. Не ослаблять CSRF/CORS веб-приложения ради мобильного клиента.

**SEC-02. Tenant isolation требует обязательного negative-test gate.**  
В `propertyDb.js` есть проверка несоответствия tenant из разных источников. Одновременно legacy auth использует fallback вида `req.db || db`. Это может быть нормально для legacy-маршрутов, но для tenant-scoped API нужно доказать, что middleware всегда подключён до бизнес-маршрута и запрос никогда не уйдёт в глобальную БД при отсутствующем tenant context.

**Рекомендация:** ввести единый tenant-scoped DB accessor для v1, запретить молчаливый fallback в tenant-scoped маршрутах и тестировать отсутствие tenant, неизвестный tenant, неактивный tenant и попытки cross-tenant replay для каждого критического домена.

**SEC-03. Production SMS-конфигурация не подтверждена.**  
В `.env.example` `SMSRU_API_ID=STUB` описан как допустимый для разработки. Сервис в этом режиме пропускает отправку SMS. Наличие шаблонного значения не доказывает production-дефект, но production gate должен гарантированно отклонять stub-провайдера. Ветка fallback в текущем SMS-сервисе использует тот же endpoint sms.ru, а не независимого поставщика, поэтому не обеспечивает отказоустойчивость при недоступности самого sms.ru.

**Рекомендация:** запретить `STUB` в production, проверить фактическую доставку и стоимость SMS, таймауты/ретраи и маскирование данных; либо назвать fallback вторым ключом того же провайдера, либо подключить независимого провайдера и проверить его отдельно.

**OPS-01. Нет актуального доказательства прохождения CI для текущей работы.**  
Последний найденный запуск основной ветки — 24 июля 2026 года — завершился ошибкой. В том запуске backend/frontend jobs прошли, но Docker Compose smoke и governance security scan упали; nightly Playwright smoke также завершился ошибкой. Исторические логи недоступны (GitHub вернул HTTP 410), поэтому причины сейчас нельзя достоверно установить. Для head PR #154 не найден успешный статус проверок.

**Рекомендация:** запустить CI на актуальном commit, сохранить артефакты и разобрать каждый failed job. Не использовать старые зелёные отдельные jobs как доказательство готовности всего релиза.

**API-01. OpenAPI описывает маршруты шире, чем строгие контракты.**  
В `docs/openapi.json` заявлены 306 путей и 160 схем; описание файла прямо говорит, что endpoint-specific request/response schemas уточняются постепенно. Поэтому число путей не означает полное контрактное покрытие.

**Рекомендация:** наращивать схемы запросов/ответов, статусы ошибок и security requirements для критических endpoint-ов; генерировать типы клиента из OpenAPI и проверять contract drift в CI. Не подключать мобильные экраны к незафиксированным контрактам.

**OPS-02. Документация быстрого запуска расходится с Compose.**  
README предлагает запускать сервисы `postgres-registry` и `postgres-object-demo`, тогда как проверенный `docker-compose.yml` определяет сервисы `db`, `redis`, `backend`, `frontend` и backup. Эти инструкции могут не работать для текущей конфигурации.

**Рекомендация:** выбрать один канонический dev setup, проверить README команда за командой на чистой машине и автоматически проверять команды из документации в smoke job.

### P2 — важно для надёжности, поддержки и масштабирования

**ARCH-01. Слишком много активных контуров для одного релиза.**  
Есть legacy API, v1 API, platform/superadmin API, несколько tenant DB, web frontend, mobile scaffold, сервисные/portfolio-модули и gated/legacy функции. Это гибко, но увеличивает когнитивную нагрузку и вероятность различий в авторизации, DTO и обработке ошибок.

**Рекомендация:** разделить домены Access, Residents, Operations, Notifications и Platform явными сервисными границами; не переписывать все модули сразу. Для каждого домена зафиксировать владельца данных, API-контракт, права, события и обязательные тесты.

**ARCH-02. Tenant DB pool cache растёт по числу объектов.**  
`propertyDb.js` создаёт pool на объект и настраивает до 20 соединений в каждом. В изученном коде pool cache хранится в Map. Для небольшого числа объектов это приемлемо, но при росте портфеля нужен контролируемый жизненный цикл пулов и бюджет соединений.

**Рекомендация:** измерять число объектов/pools/connections, ограничить общее число соединений на инстанс, определить eviction/закрытие пулов при удалении/приостановке объекта и проверить поведение при сотнях tenant-ов.

**BUILD-01. Манифесты зависимостей разделены не до конца очевидно.**  
У root, backend и frontend есть отдельные package manifests/lockfiles, но root package содержит большой набор runtime dependencies и React 19, тогда как frontend объявляет React 18. Это не обязательно runtime-конфликт — приложения устанавливаются отдельно, — но граница root tooling и продуктовых зависимостей неочевидна и усложняет supply-chain review.

**Рекомендация:** оставить в root только инструменты монорепозитория, явно описать workspace/install policy и не смешивать React/runtime dependencies фронтенда с root tooling. Не мигрировать на workspaces без проверки текущих скриптов и lockfiles.

**MOB-02. Мобильная база требует обновления и воспроизводимости.**  
В scaffold указан Expo SDK 53 / React Native 0.79, а mobile lockfile и CI job отсутствуют. Версии не были проверены командой Expo Doctor/Install Check. SDK 53 соответствует RN 0.79, но на дату аудита это уже не актуальная база для нового приложения.

**Рекомендация:** обновлять Expo SDK последовательно по официальному upgrade path, не прыгать сразу через несколько major versions; после каждого шага выполнять install check, typecheck, Android/iOS build и smoke tests. Сначала зафиксировать lockfile.

**DEPLOY-01. Производственная схема TLS зависит от внешних операционных шагов.**  
Production Compose overlay монтирует сертификаты с хоста, а документация описывает выдачу и обновление сертификатов через host-level cron. Это рабочая схема, но сама по себе не доказывает автоматическое обновление и восстановление после истечения сертификата.

**Рекомендация:** добавить мониторинг срока действия сертификата, проверку nginx config, тест reload/renewal и runbook восстановления. Отдельно проверять, что production DSN-ы, домены, cookies, CORS, SMS, Redis и upload signing secrets согласованы между окружениями.

**LEGAL-01. Юридические документы и технические контроли не равны подтверждённому соответствию.**  
В репозитории есть threat model, privacy и Russia-readiness specs, но они сами обозначены как draft/spec. Не было доступа к production-хостингу, договорам, реальным процессам обработки данных и evidence.

**Рекомендация:** перед реальным пилотом назначить ответственного за обработку ПДн, проверить локализацию, роли оператора/обработчика, сроки хранения, основания обработки, права субъектов, доступы персонала, реагирование на инциденты и договоры с поставщиками. Нужна отдельная юридическая оценка; данный аудит не является заключением по 152-ФЗ.

**GOV-01. Публичный репозиторий и лицензирование требуют ясной политики.**  
Репозиторий публичный; root `package.json` указывает ISC, но в проверенном корне не обнаружен файл LICENSE. Публичность повышает требования к проверке секретов и случайно добавленных данных.

**Рекомендация:** определить, должен ли исходный код быть публичным; добавить корректную лицензию/NOTICE либо сделать репозиторий приватным, если это соответствует бизнес-модели; сохранить secret scanning и проверку отсутствия персональных/production-данных.

## 5. Проверки, которые нужно выполнить локально или в CI

Эти команды задокументированы в проекте, но в рамках данного аудита не запускались:

1. `npm ci` в root, `backend/`, `frontend/`; сравнить lockfiles и Node version.
2. `npm run test`, `npm run verify`, затем `npm run verify:strict`.
3. Backend: `npm run test:ci`, `npm run test:coverage:critical`, `npm run test:contract`, `npm run test:detect-open-handles`.
4. Frontend: lint, typecheck, test, production build и bundle budget.
5. `npm run openapi:drift`, `npm run frontend:v1-contract-coverage`, `npm run backend:v1-property-scope-audit`.
6. Чистый Docker Compose запуск, healthchecks, миграции registry + tenant DB, restart после сбоя Redis/DB.
7. Backup → restore в изолированную БД с подтверждением целостности, а не только успешного завершения скрипта.
8. Access E2E: валидный/истёкший/отозванный QR, повторное использование, неправильная зона/время, cross-tenant, offline, manual override, журналирование.
9. Security test: OTP abuse, refresh-token replay, отзыв сессии, CSRF, роль/объект/действие, upload authorization, отсутствие tenant context.
10. Mobile: Expo install check, typecheck, signed/internal Android build, iOS build, session expiry, сеть/ошибки, accessibility и update path.

## 6. Критерий готовности

Проект можно считать кандидатом на пилот только когда:
- свежий CI зелёный на конкретном commit;
- миграции проверены на чистой БД и безопасно повторяемы;
- tenant/role negative tests проходят;
- QR проверяет сервер, а не доверяет клиенту;
- SMS и production secrets подтверждены в staging;
- backup реально восстановлен;
- Android/iOS сборки установлены и проверены;
- СКУД проверена на тестовом контуре;
- privacy/retention/incident runbooks утверждены владельцами.

**Итог:** проект не выглядит пустой заготовкой — в нём много уже сделанной инженерной работы. Главная задача теперь не добавить ещё десятки модулей, а доказать целостность существующих границ, привести запуск/контракты к одному стандарту и собрать ограниченный, проверяемый resident/guard MVP.
