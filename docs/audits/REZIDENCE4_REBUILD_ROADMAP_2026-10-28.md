# План глубокой переработки Rezidence4

**Дата решения:** 28 октября 2026  
**Стратегия:** глубокая переработка на основе существующего кода; web + Android/iOS; сначала код и тесты, затем сервер.  
**Данные:** проект не вводился в эксплуатацию, реальных данных и production-серверов нет.

## 1. Принятое техническое решение

Не делать переписывание ради переписывания и не считать старую реализацию неприкосновенной. Использовать Rezidence4 как исходный материал: сохранять модули только после проверки контрактов, тестируемости, безопасности и необходимости для первого релиза.

Отсутствие production-данных снимает риск миграции реальных пользовательских данных, но не отменяет необходимости проверять схему БД, миграции, API и tenant isolation. Не удалять целые подсистемы до инвентаризации зависимостей и тестов. Для первой версии допустимы breaking changes в неиспользуемых внутренних API, если они документированы и покрыты тестами.

## 2. Продукт первого релиза

### Web
- **Жилец:** вход, просмотр квартиры в рамках полномочий, создание/просмотр/отмена пропуска, безопасная передача гостю.
- **Охрана:** поиск и проверка QR/кода, ручной поиск по разрешённым атрибутам, решение сервера, журнал визитов и инцидентов.
- **Администратор:** жильцы/квартиры, роли, сотрудники, правила пропусков, аудит действий и состояние интеграций.

### Android/iOS
- Сначала приложение жильца: вход, квартира, создать/посмотреть/отменить/поделиться пропуском.
- Охрану на первом этапе реализовать как mobile-first web workspace: это быстрее для тестирования на постах и не требует параллельно выпускать второе нативное приложение.
- Нативный режим охраны рассматривать после подтверждения требований к камере, устройствам и offline-процессу.

### Не включать в первый релиз
- интеграцию с реальной СКУД без тестового стенда и спецификации производителя;
- сложную аналитику, чаты, аренду и второстепенные SaaS-модули;
- offline-разрешение на проход;
- push до стабилизации базового сценария пропуска.

## 3. Архитектурные принципы

1. Backend — единственный источник истины для статуса пропуска и решения о допуске.
2. Web и mobile используют версионированный API и общие DTO/enum; бизнес-правила не дублируются в клиентах.
3. Browser auth сохраняет безопасный cookie + CSRF-поток. Native auth оформляется отдельным контрактом с короткоживущим access token, ротацией и отзывом refresh token, secure storage ОС и явным logout.
4. Tenant context обязателен для tenant-scoped запросов. Нельзя незаметно переключаться на глобальную БД при отсутствии tenant.
5. QR содержит непрозрачный короткоживущий токен без ФИО, телефона, квартиры или иных персональных данных. QR — идентификатор для server-side проверки, а не доказательство допуска.
6. Решение проверяет срок, статус, отзыв, объект, точку/зону, право оператора, правила повторного предъявления и аудитирует результат.
7. Все окружения и данные синтетические до приёмки. Никаких настоящих телефонов жильцов, ключей или production endpoint в Git.
8. Внешние интеграции подключаются через адаптеры и имеют контрактные тесты; до наличия тестового оборудования используются явные sandbox/stub-режимы, которые запрещены в production.

## 4. Этапы, задачи и критерии приёмки

### Этап 0 — инвентаризация и воспроизводимость
- [ ] Составить карту модулей: активные API, legacy API, tenant/platform API, web, mobile, миграции, фоновые задачи.
- [ ] Выбрать поддерживаемую версию Node и закрепить её во всех окружениях.
- [ ] Привести README, Compose, env example и имена сервисов к одному сценарию запуска.
- [ ] Зафиксировать команды проверки и сохранить baseline результатов.
- [ ] Создать synthetic seed для одного тестового ЖК, квартир, пользователей, сотрудников и пропусков.
- [ ] Убедиться, что чистая БД поднимается только из миграций, повторный запуск не повреждает схему.
- [ ] Добавить/обновить CI, чтобы он проверял backend, web и mobile отдельно.

**Gate:** чистая установка и тесты воспроизводимы; известны все проваленные проверки и есть владельцы исправлений.

### Этап 1 — границы backend и безопасность
- [ ] Определить домены: identity/session, property/tenant, residents/units, passes/visits, guard, audit, notifications, integrations.
- [ ] Для каждого домена закрепить источник данных, DTO, permissions и API owner.
- [ ] Ввести единый tenant-scoped DB accessor для v1; запретить fallback к глобальной БД в tenant-scoped маршрутах.
- [ ] Добавить отрицательные тесты cross-tenant для чтения, изменения, отмены пропуска и проверки QR.
- [ ] Проверить RBAC и scopes на сервере, а не только скрытием кнопок.
- [ ] Зафиксировать native session contract и покрыть OTP, rate limit, refresh rotation, logout, revoke, expiry и деактивацию аккаунта.
- [ ] Production configuration validation должна отклонять SMS stub и слабые/отсутствующие секреты.
- [ ] Проверить логирование: не писать OTP, токены, QR secret и избыточные персональные данные.

**Gate:** tenant isolation и права доказаны негативными тестами; web auth не ослаблен ради native.

### Этап 2 — контракт и модель пропусков
- [ ] Утвердить OpenAPI request/response schemas для create/list/get/cancel/share/verify.
- [ ] Сгенерировать типы web/mobile из контракта либо обеспечить единую типизацию другим способом.
- [ ] Определить состояния пропуска и разрешённые переходы; переходы валидируются backend.
- [ ] Определить политику QR: TTL, одноразовость/повторное использование, отзыв, допустимые checkpoints, защита от replay.
- [ ] Добавить audit event для создания, передачи, отмены, проверки, отказа и ручного override.
- [ ] Проверить идемпотентность повторных запросов там, где повтор может создать дубликат.

**Gate:** контрактные и интеграционные тесты покрывают все состояния и запрещённые переходы.

### Этап 3 — web MVP
- [ ] Подключить реальные v1 API к интерфейсам жильца, охраны и администратора.
- [ ] Реализовать loading/empty/error/permission/offline states.
- [ ] Сделать поиск пропуска по QR и ограниченным ручным критериям.
- [ ] Отображать серверное решение с понятной причиной; неизвестный статус — не разрешать проход.
- [ ] Покрыть Playwright happy path и негативные сценарии.
- [ ] Проверить адаптивность на типовых мобильных устройствах поста охраны.

**Gate:** E2E проходит от входа жильца до серверной проверки пропуска и появления события в журнале.

### Этап 4 — mobile MVP
- [ ] Последовательно обновить Expo SDK до выбранной стабильной версии; не менять SDK, React Native и native packages хаотично одним коммитом.
- [ ] Зафиксировать mobile lockfile и включить mobile CI.
- [ ] Реализовать native login/session, secure storage, refresh, logout и обработку истёкшей сессии.
- [ ] Реализовать список квартир/пропусков только в пределах серверных прав.
- [ ] Реализовать создание, список, отмену и безопасную передачу пропуска.
- [ ] Добавить deep links только с серверной проверкой и безопасным fallback.
- [ ] Добавить тесты API helper, auth state и ключевых экранов.
- [ ] Собрать Android и iOS development builds; проверить физическое устройство и слабую сеть.

**Gate:** житель выполняет основной сценарий на Android и iOS; токены не попадают в логи и не хранятся в AsyncStorage.

### Этап 5 — тестирование и подготовка к пилоту
- [ ] Запустить полный backend/web/mobile CI на одном PR.
- [ ] Проверить миграции на пустой БД и seed повторно.
- [ ] Проверить нагрузку для сценариев login/list/create/verify и rate limiting.
- [ ] Выполнить backup/restore drill и документировать RPO/RTO.
- [ ] Проверить мониторинг, алерты, журнал ошибок и expiry TLS.
- [ ] Подготовить runbooks: сбой SMS, Redis/DB, потеря связи у охраны, отзыв сессии, инцидент доступа.
- [ ] Провести security review и проверить актуальные требования к персональным данным РФ до загрузки реальных данных.
- [ ] Подключать СКУД только после получения модели/протокола устройства и тестового стенда.

**Gate:** письменный go/no-go checklist закрыт; только после этого создавать production-среду и подключать реальные данные.

## 5. Обязательная матрица тестов

| Область | Положительные тесты | Отрицательные тесты |
|---|---|---|
| Авторизация | OTP, обновление сессии, logout | brute force, replay, revoked/expired token |
| Tenant | пользователь видит свой ЖК | отсутствующий/неизвестный tenant, доступ к чужому ЖК |
| Роли | разрешённое действие | житель вызывает admin/guard endpoint |
| Пропуска | создать, получить, отменить | истёкший, отменённый, чужой объект, неверный переход |
| QR/допуск | валидный пропуск в окне | replay, неверная точка, нет связи, подмена UI |
| Web/mobile | загрузка, пустое состояние, восстановление ошибки | 401/403/429/5xx, плохая сеть, истёкшая сессия |
| Operations | чистый запуск, backup/restore | недоступность Redis/DB, неверная конфигурация |

## 6. Рекомендуемый порядок pull request-ов

1. **PR A — Baseline & docs:** актуализировать план, единый локальный запуск и список команд проверки.
2. **PR B — CI reproducibility:** lockfiles, Node pinning, backend/web/mobile jobs, smoke test.
3. **PR C — Tenant/auth hardening:** DB accessor, negative tests, native auth contract.
4. **PR D — Pass API contract:** schemas, state machine, verify endpoint, audit events.
5. **PR E — Web MVP:** жилец + охрана + администрация на реальных API.
6. **PR F — Mobile resident MVP:** secure session + пропуска.
7. **PR G — Release readiness:** backup/restore, monitoring, security review, staging acceptance.

Каждый PR должен быть небольшим, иметь автоматические проверки и не смешивать форматирование/рефакторинг с изменением бизнес-правил.

## 7. Definition of Done

Задача готова только когда:
- код и тесты добавлены вместе;
- API/DTO и документация согласованы;
- ошибки и права обработаны на сервере;
- нет секретов и настоящих персональных данных;
- обязательные CI checks зелёные;
- критический сценарий воспроизводим на чистом окружении;
- известные ограничения задокументированы.
