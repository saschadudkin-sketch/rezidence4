# Рекомендованный план улучшенной версии Rezidence4

**Цель:** развивать существующий проект без рискованного rewrite, сохраняя работающие API и данные. Первым целевым продуктом считать один реальный ЖК — «Резиденции Замоскворечья» — с архитектурой, которую можно масштабировать на другие объекты.

## Решение по стратегии

**Не переписывать весь backend и web-клиент с нуля.** Сначала стабилизировать текущую платформу, выделить один end-to-end сценарий и затем поэтапно расширять его. Полный rewrite одновременно API, базы, web, mobile и SKUD создаст риск потери уже реализованных правил доступа и tenant isolation.

## Целевая версия

### Resident app — Android/iOS
- вход по номеру телефона и OTP;
- объект/квартира и понятное состояние доступа;
- создать пропуск за менее чем минуту: гость, курьер, такси, мастер, автомобиль;
- повторить недавний пропуск;
- список активных/ожидаемых/истёкших, отмена и изменение;
- безопасно поделиться пропуском;
- уведомления об изменении статуса и визите;
- ясные offline/error states; приложение никогда не объявляет доступ разрешённым без ответа сервера.

### Guard workspace — mobile-first web или отдельный staff mode
- поиск по QR, коду, номеру автомобиля и гостю;
- ответ сервера: разрешён / запрещён / нужна ручная проверка / нет связи;
- checkpoint/zone, время, правила и причина решения;
- аудит каждого override с сотрудником, причиной и последующей проверкой;
- offline-кэш ограниченных данных с явной маркировкой; никаких локальных approvals;
- журнал визитов и инцидентов.

### Admin workspace — web
- жильцы, квартиры/объекты, роли и сроки полномочий;
- сотрудники и подрядчики;
- зоны, точки доступа и политики;
- журнал действий и расследование инцидентов;
- health/status интеграций, очереди уведомлений и ошибки;
- отчётность без доступа к данным чужих объектов.

## Этапы внедрения

### Этап 0 — воспроизводимая база
- получить чистую установку на Node version из `.nvmrc`;
- исправить README/Compose расхождения;
- получить свежий зелёный CI и зафиксировать baseline;
- сформировать актуальный OpenAPI contract map;
- зафиксировать миграционный и backup/restore baseline;
- создать мобильный lockfile и проверить Expo dependency alignment.

**Gate:** установка, тесты, build и healthchecks воспроизводимы на чистом окружении.

### Этап 1 — безопасная сессия
- утвердить native auth/session contract;
- сохранить web cookie + CSRF flow;
- добавить mobile refresh rotation/revocation, logout, session expiry и account deactivation;
- тестировать brute force, replay, revocation и tenant mismatch;
- запретить production с `SMSRU_API_ID=STUB`.

**Gate:** integration tests доказывают безопасный вход/выход и восстановление сессии без обхода tenant scope.

### Этап 2 — resident MVP
- реализовать только создание, список, отмену и повтор пропуска;
- подключить формы к подтверждённым API v1 DTO;
- добавить loading/empty/error/offline states;
- push и deep links — после стабилизации базовых сценариев;
- тестировать UX на реальных Android/iPhone и слабой сети.

**Gate:** житель проходит сценарий «войти → создать пропуск → поделиться → отменить» без ручного вмешательства разработчика.

### Этап 3 — guard MVP и доступ
- единый серверный verify endpoint для QR/manual/plate;
- короткоживущий непрозрачный QR token без персональных данных;
- серверные проверки времени, статуса, tenant, checkpoint/zone, revocation и replay;
- аудит решения и override;
- negative E2E: чужой объект, истёкший/отозванный/повторный QR, отсутствие сети;
- безопасная процедура деградации и ручной проверки.

**Gate:** в тестовом контуре нельзя получить разрешение локальной подменой UI или повторным предъявлением отозванного QR.

### Этап 4 — администрация и операции
- lifecycle жильца/квартиры;
- роли, scopes, временные полномочия;
- staff/contractor queues;
- уведомления/outbox с retry, dedupe и наблюдаемостью;
- журнал аудита, инциденты и отчёты;
- явное разделение функций property admin и platform superadmin.

**Gate:** все критические изменения имеют audit event, permission check и tenant-scoped tests.

### Этап 5 — SKUD, production и закрытое распространение
- получить точные модель/производителя/протокол СКУД и тестовый контур;
- сделать provider adapter с таймаутами, idempotency, health checks и журналом команд;
- Android internal distribution (закрытый APK/managed distribution) и iOS TestFlight/private distribution — выбрать по модели устройств и аккаунтам;
- подписанные сборки, секреты только в CI secret store, инструкции обновления/отзыва;
- проверить локализацию ПДн, retention, права доступа, incident response и backup restore;
- ограниченный пилот на одном объекте с обучением охраны.

**Gate:** подписанные сборки, успешная приёмка оборудования, восстановление из backup, утверждённые runbooks и владелец поддержки.

## Архитектурные правила

1. PostgreSQL остаётся источником истины для жильцов, пропусков и решений доступа.
2. Клиент не содержит правил, которые разрешают проход; только отображает решение backend.
3. Каждая v1 операция получает tenant context до бизнес-логики.
4. Роли и scopes проверяются на сервере на каждом запросе.
5. Access, Residents, Operations, Notifications и Platform имеют отдельные сервисные границы, но не обязательно отдельные микросервисы.
6. События аудита для доступа/админских действий неизменяемы для обычных пользователей и имеют actor, tenant, checkpoint, timestamp, reason/correlation ID.
7. Контракты API генерируют типы клиента; не дублировать DTO вручную в web/mobile.
8. Каждый production gate требует исполняемого теста или проверяемого evidence, а не только документа.
9. Не подключать реальные ПДн и production СКУД в dev/test.
10. Не делать массовую миграцию БД или rewrite до baseline backup, restore drill и contract tests.

## Что не делать сейчас

- Не переписывать всю систему на другой backend framework.
- Не дробить модули на микросервисы без измеримой причины.
- Не реализовывать offline approval для пропусков.
- Не добавлять биометрию как способ авторизации.
- Не делать push, чаты, бронирования и дополнительные SaaS-модули при неготовых входе, пропусках и проверке охраной.
- Не сливать мобильный PR до зелёных проверок и реальных device builds.

## Рекомендуемый первый релиз

Минимальный рабочий релиз должен включать только:
1. OTP login;
2. resident + unit context;
3. создание/список/отмена пропуска;
4. share pass;
5. guard verify QR/manual;
6. visit log + audit;
7. admin resident/pass support;
8. monitoring, backup/restore и internal distribution.

Это даст законченный путь для жильца и охраны, после чего можно безопасно расширять платформу.
