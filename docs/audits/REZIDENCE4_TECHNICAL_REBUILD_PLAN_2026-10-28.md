# Rezidence4 — технический план глубокой переработки

**Репозиторий:** saschadudkin-sketch/rezidence4  
**Рабочая ветка:** codex/mobile-app-foundation  
**Статус:** план и статический аудит; это не отчёт о выполненных runtime-тестах.

## Цель

Подготовить первую проверяемую версию системы пропусков для ЖК «Резиденции Замоскворечья»: веб-интерфейсы жильца, охраны и администратора плюс нативное приложение Android/iOS для жильца. Сначала код, автоматические тесты и синтетические данные; сервер и настоящие данные — после прохождения release gates.

Проект не вводился в эксплуатацию и не содержит настоящих данных. Поэтому нет обязательства сохранять старую схему ради миграции реальных пользователей. Но существующие модули нельзя выбрасывать без анализа: они могут содержать полезные проверки, контракты и бизнес-правила.

## Архитектурная цель

Resident Web, Guard Web (mobile-first), Admin Web и Resident Mobile используют единый versioned API (/api/v1), который вызывает доменные сервисы: Identity/Sessions, Residents/Units, Passes/Visits, Guard Verification, Audit и Notifications/Integrations. Доступ к Registry DB и Property DB выполняется только через tenant-scoped repositories.

Схема показывает целевые границы, а не заявление, что такая структура полностью реализована сейчас.

## 2. Целевые доменные границы

| Домен | Ответственность | Главный инвариант |
|---|---|---|
| Identity & Sessions | OTP, access/refresh sessions, logout/revoke | токены ограничены по сроку и правам; секреты не логируются |
| Tenant & Property | объект, hostname, tenant context, активность | каждый tenant-запрос однозначно привязан к объекту |
| Residents & Units | связь пользователя с квартирой и полномочия | пользователь видит только разрешённые ему объекты/квартиры |
| Passes | жизненный цикл пропуска | переходы состояний проверяет backend |
| Guard Verification | QR/manual lookup, checkpoint, решение | только сервер возвращает окончательное решение |
| Visits & Audit | события проверок и действий | события имеют actor, tenant, timestamp, outcome и корреляцию |
| Notifications | SMS/push и очереди | stub-режим явно маркирован и запрещён в production |
| Integrations | адаптеры СКУД и внешних провайдеров | внешняя интеграция изолирована от доменной логики |

Не обязательно создавать микросервисы. На первом этапе предпочтителен модульный backend с явными границами и одной понятной транзакционной моделью.

## 3. Безопасность tenant и ролей

- Все tenant-scoped v1 handlers получают проверенный tenant context до обращения к данным.
- Создать единый repository/DB accessor, который падает закрыто, если tenant отсутствует или неактивен; никаких неявных переходов на глобальную БД.
- Платформенные маршруты и маршруты отдельного ЖК имеют разные middleware и явные тесты.
- Проверить, что tenant нельзя сменить одним заголовком, параметром URL или изменённым claim.
- Разрешения проверяются на сервере на каждом чтении и изменении.
- В негативные тесты включить IDOR, чужую квартиру, чужой пропуск, отмену чужого пропуска, QR от другого ЖК и вызов admin/guard API жителем.
- Логи и ошибки не должны раскрывать OTP, токены, полный QR secret и ненужные персональные данные.

## 4. Native auth

Web cookie + CSRF поток остаётся предназначенным для браузера. Native client получает отдельный контракт после тестирования:
- access token короткого срока действия;
- refresh token с ротацией, хранением хэша на сервере и отзывом;
- secure storage ОС на устройстве;
- обработка refresh race, logout, revoked/expired session и деактивированного пользователя;
- ограничение частоты OTP и одинаковые внешние ответы, не раскрывающие наличие аккаунта.

До реализации native auth мобильное приложение остаётся prototype и не используется для допуска.

## 5. Пропуска и серверная проверка

Рекомендуемая минимальная модель:
- Pass: tenant, issuer, resident/unit scope, visitor type, valid_from, valid_until, status, created_at, updated_at;
- PassCredential: хэш/идентификатор случайного QR token, срок действия, revoke/use policy;
- VisitEvent: pass reference, checkpoint, operator, timestamp, result, reason code, correlation ID;
- AuditEvent: actor, tenant, action, target, outcome, timestamp и минимальный metadata.

Это концептуальная модель; перед миграциями её нужно сопоставить с существующими таблицами, не создавая дубликаты.

Проверка на сервере должна включать: token validity, tenant match, pass status, time window, revocation, checkpoint/zone policy, actor permissions и replay policy. При отсутствии сети ответ — «не удалось проверить / нужна ручная процедура», а не «разрешено». Ручной override требует роли, причины и audit event.

## 6. Web и mobile UX

**Жилец:** вход → контекст квартиры → создать пропуск → посмотреть/передать → отменить. Для каждой операции есть loading, empty, error, forbidden и session-expired states.

**Охрана:** быстрое сканирование или ручной поиск → явное решение сервера → причина/ограничения → журнал события. Состояния «отказано», «не найдено», «истёк», «отозван», «не та точка», «нет связи» должны различаться.

**Администратор:** управление жильцами, квартирами, ролями и сотрудниками, аудит и состояние интеграций. Критичные действия подтверждаются и журналируются.

**Mobile:** на первом этапе только жильцы. Не делать параллельно два разных мобильных клиента до проверки потребности охраны в нативной камере или офлайн-функциях.

## 7. Сборка, версии и CI

- Закрепить Node version и использовать npm ci для пакетов с lockfile.
- Проверять backend tests, contract tests, coverage-critical и open handles.
- Проверять frontend lint, tests, typecheck, production build и Playwright E2E.
- Добавить отдельный mobile job после создания и коммита mobile lockfile: dependency check, typecheck, unit tests, Expo Doctor; Android/iOS builds — отдельный release/staging job.
- Mobile сейчас использует Expo SDK 53 и не имеет lockfile. Не обновлять всё одним неконтролируемым коммитом: SDK 53 → 54 → 55 → 56 → 57 (или отдельно утверждённая более новая стабильная версия), на каждом шаге запускать expo install --fix, expo-doctor, typecheck и сборку. SDK 58 появился 15 октября 2026; его целесообразно оценить отдельно перед выбором target.
- Для GitHub Actions использовать pinning действий по reviewed SHA при усилении production pipeline; никакие секреты не нужны для обычных тестов.
- PR должен показывать реальные результаты CI, а не просто наличие workflow-файла.

## 8. Definition of Done для MVP

1. Чистая установка и миграции воспроизводимы.
2. Synthetic seed не содержит реальных персональных данных.
3. Backend, web и mobile проходят обязательные проверки.
4. Сквозной E2E: OTP/session → создание пропуска → отображение QR → server verification → audit/visit event → отмена → повторная проверка отклонена.
5. Негативные tenant/role/expiry/replay/no-network тесты проходят.
6. Android и iOS development builds проверены на устройствах; неподдерживаемые сценарии явно описаны.
7. Документация локального запуска, тестирования, восстановления БД и реагирования на сбой актуальна.
8. Ни один production endpoint, секрет или реальная запись не добавлены в репозиторий.
